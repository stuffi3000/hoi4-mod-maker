# HOI4 Map Maker export contract

This page is repository-specific. The other pages in `docs/wiki/` describe what the HOI4 engine expects; this page records what the current tool actually generates, preserves, repairs, or leaves for a later content workflow. It is the reference to update when an exporter writer changes.

**Review date:** 19 September 2026
**Acceptance profile used by the map audit:** HOI4 1.19.3.0, 5,632x2,048 map, custom-map foundation plus a disposable scenario scaffold.

## Four questions for every exported file

Every output file must have one explicit status in the export manifest:

| Status | Meaning | Required action |
| --- | --- | --- |
| Generated | The exporter creates the file from project data or deterministic defaults | Validate the generated bytes and references |
| Preserved | The importer supplied bytes and the user did not edit that asset | Restore the original bytes and record the source hash |
| Inherited | The MOD intentionally relies on vanilla or a dependency | Record the dependency and do not report absence as an exporter bug |
| Intentionally omitted | The selected version/profile does not need the file | Record the reason and version/profile |
| Unsupported | The source contains a file the tool cannot safely round-trip | Warn or fail before export; never silently discard it |

“Present in the output directory” is not a sufficient status. An empty compatibility file, a stale inherited asset, and a newly generated map layer have different engine and maintenance implications.

## Source of truth and export flow

The project file and its managers are the editable source of truth:

```text
.hoi4proj
  -> immutable snapshot + selected GameTarget
  -> planner + staged profile writers
  -> foundation/acceptance/scaffold artifact
  -> manifest + static verifier
  -> isolated HOI4 engine acceptance run
```

`export/mod_exporter.py` intentionally exports from working copies for several repair/compaction steps. Tiny provinces can be merged, oversized province bounding boxes can be trimmed, and optional ID compaction can remap manager references on the export copy. These mutations must be reported in the manifest with before/after counts and an ID mapping; content authors must never assume that a silent export repair is harmless.

The modern export API selects `foundation`, `acceptance`, `scaffold`, or
`legacy_full`. The old scope dictionary remains an adapter and emits a
deprecation warning for new planner/facade callers. A partial export is valid
only when its inherited files and dependencies are documented. The static
verifier is a structural gate, not an engine acceptance test.

## Current output contract

| Area | Current writer/behavior | Contract or known limitation |
| --- | --- | --- |
| Province raster | `export/mod_exporter.py` writes `map/provinces.bmp` from the project map | IDs, colors, classification, dimensions, connectivity, and edge behavior must be checked together |
| Province definitions | `definition.csv` is written after coastal/building calculations | The final CSV must match the final raster and final land/sea/lake/coastal decisions |
| Height/terrain/rivers | Generated from project layers or fallbacks; terrain is synchronized with tile type | Palette/index and target-version art contracts still need profile validation |
| Trees/cities/normal | Trees and cities are generated; normal may be generated or restored from imported assets | Dimensions and asset semantics require target-game testing |
| DDS map art | Colormap, water, and FOW DDS files are generated or restored as grouped assets | Compression, headers, and mipmaps must be verified; generated art is not automatically production art |
| States | Manager states are copied to export files; orphan land can be adopted and IDs may be compacted | State membership and IDs are foundation data; owner/name/category/history are scenario content |
| Strategic regions | Manager regions are written to `map/strategicregions/`, otherwise generated from the map | IDs, complete province coverage, contiguity, and weather positions must be checked |
| Supply/railways | Manager data is used when present; otherwise fallback nodes and railways are generated | Fallback data is scaffolding, not a designed logistics network |
| Legacy supply areas | `_write_supply_areas()` still writes `map/supplyareas/*.txt` when supply export is enabled | The old system is deprecated from 1.11; keep only as a compatibility artifact with an explicit legacy status |
| Adjacencies | Manager data is written when present; otherwise header plus sentinel is emitted | No special straits/canals are implied by an empty file; author and validate them explicitly |
| Buildings | Foundation uses reviewed manager placements when available; legacy/scaffold paths retain deterministic compatibility helpers | Coordinates are still validated against the final raster; generated records remain provisional until reviewed |
| Positions | Foundation uses the placement contract; legacy paths may retain centroid compatibility output | It is not final unit/city/port placement until provenance and surface ownership pass review |
| Unit stacks | `write_empty_unitstacks()` emits an empty `unitstacks.txt` | The current target installation contains substantive unit-stack data; this is a known project gap, not a proof that the file is optional |
| Airports/rocket sites | The compatibility writer emits empty legacy files | Version-gate or omit them when the selected game no longer reads them |
| Countries | Manager countries or a fallback country are generated, with flags, history, ideas, bookmark, and localization scaffolding | Generated scenario tags must be unique and isolated from vanilla; detailed content is not yet a full editor contract |
| Replacement paths | The replacement scrubber creates a full-conversion override tree | Every replacement directory needs an inventory; broad replacement can remove inherited definitions |
| Defines | Staged `scaffold` calculates `MAX_PROVINCES` from the actual province count; `legacy_full` retains its 25,000 floor for compatibility | The selected profile and reason must be recorded in the manifest; new callers should not inherit the legacy floor accidentally |

## ID and reference contract

Freeze the IDs and write an export mapping before ordinary content is authored:

| Identifier | Consumers | Migration consequence |
| --- | --- | --- |
| Province ID | `provinces.bmp`, `definition.csv`, states, regions, buildings, positions, supply, railways, adjacencies, VPs, scripts | Raster or ID changes require a coordinated reference migration |
| State ID | `history/states/*.txt`, country capitals, owners, buildings, strategic grouping, bookmarks/scripts | State compaction changes history and content references |
| Strategic-region ID | `map/strategicregions/*.txt`, weather positions, air/naval scripts | Region changes can invalidate weather, air, naval, and script references |
| Country tag | Country definition/history, states, localization, flags, politics, scripts, OOB | Tag collision can bind generated content to vanilla or another MOD |
| Building/object coordinate | `buildings.txt`, positions, ports, map overlays | Coordinate changes can move an object across province or terrain boundaries |
| Logistics edge | `railways.txt`, `adjacencies.csv`, supply nodes, map topology | Endpoint/ordering changes alter gameplay networks and may invalidate route data |

The mapping should include removed/merged IDs, not only surviving IDs. If a writer repairs the map during export, the user interface should show the mutation and the manifest should make it reproducible.

## Foundation versus content handoff

The map foundation owns:

- target version/profile, dimensions, coordinate/wrap convention, and raster formats;
- province IDs, colors, classes, geometry, coastline, terrain, height, rivers, trees, and map-art provenance;
- state province membership and stable state IDs;
- strategic-region membership and weather geometry;
- logistics topology, special adjacencies, building/port positions, and validation results;
- generated/inherited/omitted asset decisions and the export manifest.

The later content workflow owns:

- state names, categories, owners, controllers, cores, manpower, resources, and final state history;
- country tags, names, flags, leaders, characters, ideologies, ideas, focuses, events, decisions, technologies, equipment, OOBs, AI, diplomacy, and balance;
- final localization and manual art polish.

Starter country/state data may be useful for a disposable test scenario, but it must be labeled as scaffolding. A production foundation export should not silently add randomized gameplay content or consume vanilla country tags.

## Minimum definition of done

Before declaring a foundation export ready for downstream development, require:

- a selected game executable/version and map profile;
- a clean unique-tag test MOD with synchronized descriptors and a recorded dependency/replacement policy;
- a manifest containing source/output hashes, generated/preserved/inherited/omitted assets, repairs, warnings, and ID mappings;
- exact static checks for raster, definition, palettes, dimensions, states, regions, logistics, buildings, coordinates, countries, and localization;
- an explicit decision for special adjacencies and legacy supply-area files;
- reviewed or intentionally provisional unit, VP, port, and building positions;
- target-version validation of terrain registries, DDS headers/compression/mips, trees, normals, and optional map assets;
- main-menu load, new-game setup, at least 30 days of ticking, map-mode/supply checks, save/reload, and a clean log review;
- a frozen raster/ID/topology snapshot before content authors begin ordinary scripts and history.
