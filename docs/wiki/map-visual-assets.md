# HOI4 map visual assets and raster contracts

Map art is not ordinary illustration. HOI4 reads several indexed bitmaps and
DDS files as data tables. Preserve the source asset's technical format even
when the pixels are being generated by the tool.

## Bitmap rules

| File | Typical format | Meaning |
| --- | --- | --- |
| `provinces.bmp` | 24-bit RGB, uncompressed, hard edges | Province color identity |
| `terrain.bmp` | 8-bit indexed | Graphical terrain palette index |
| `heightmap.bmp` | 8-bit grayscale/indexed | Elevation; black is 0 and white is about 25.5 world units |
| `rivers.bmp` | 8-bit indexed | One-pixel orthogonal river paths and sources |
| `trees.bmp` | 8-bit indexed | Tree/map-object IDs and density |
| `cities.bmp` | 8-bit indexed | City group color indices |
| `world_normal.bmp` | 24-bit RGB | Surface normals for lighting |

For the full-size map files, use the exact dimensions required by the selected
profile. The province, terrain, height, and river maps normally have identical
dimensions. `trees.bmp` is an intentional exception in many maps: its
resolution controls the density of static objects. Do not resize it merely to
make every file equal without checking the target vanilla map.

The engine expects Windows BMP structures with no compression. The DIB header
must be compatible with the engine (the wiki specifically warns about editors
that write an unsupported color-space/DIB variant). In indexed files, the
palette index is the data; matching a visible RGB color is not enough.

Practical rules for generated or edited maps:

- Never anti-alias `provinces.bmp`; an edge blend creates new province colors.
- Do not convert indexed files to RGB and back with a newly generated palette.
- Keep the terrain, river, tree, and city palettes from the selected vanilla
  profile or explicitly generate a matching palette from installed definitions.
- Validate the file header, bit depth, orientation, dimensions, palette, and
  pixel indices before starting the game.

## Height and coordinates

The standard height convention maps grayscale 0..255 to approximately
`Y = 0..25.5`. The default sea surface is near grayscale 95 (`Y = 9.5`), so
the heightmap and all generated object positions must agree on the water line.
Smooth transitions are preferable at coastlines and mountain edges; a normal
map contributes to the rendered slope but does not repair incorrect elevation.

`X` is the province-map column. `Z` is the world vertical coordinate and is
opposite the usual top-to-bottom image row direction. The repository's map
writers should centralize this conversion instead of each writer inventing its
own formula.

## Graphical terrain and material atlases

`common/terrain/*.txt` connects graphical terrain entries to palette indices,
provincial terrain types, and material textures. A graphical terrain entry can
also request city spawning or permanent snow. The default material files are
under `map/terrain/atlas*.dds` and `atlas_normal*.dds`.

The base-game atlas convention is a square 4 by 4 arrangement of 512-pixel
tiles for the first level, with lower-resolution atlases for farther zoom. The
selected game profile must determine the actual atlas dimensions and format.
The wiki documents DXT5 compression and mipmaps for the terrain atlases; do
not apply the no-mipmap colormap rule to them.

The tool already reads the installed terrain registry in
`services/game_assets.py`. New terrain generation should use that mapping:

```text
terrain.bmp palette index -> graphical terrain entry -> atlas texture tile
definition.csv terrain      -> gameplay terrain modifiers
```

The same graphical terrain index can have a different visible RGB value in a
different palette. The index and its target definition are the stable parts.

## Rivers

`rivers.bmp` uses indexed flow markers and widths. The standard palette is:

| Index | Meaning |
| ---: | --- |
| 0 | Green source marker; one main source per contiguous river |
| 1 | Red flow-in marker joining a branch to a main river |
| 2 | Yellow flow-out marker splitting a river |
| 3..11 | River widths from narrow to widest |

Rivers must be one pixel thick, connect orthogonally rather than diagonally,
and use a valid source/branch topology. Long rivers also affect performance
because they behave like level-one railway connections. A river crossing is
determined where a province-center path intersects a river pixel, so paths and
rivers should be designed together.

## Trees, cities, and map objects

`trees.bmp` indexes map objects that are defined as `mapobject_N` entities in
`gfx/entities/*.gfx` or the target profile's equivalent. The `tree = { ... }`
line in `default.map` declares which indices count as trees for automatic
terrain assignment. Do not hard-code the vanilla set when the tool is importing
a custom terrain definition.

City rendering is also two-layered:

- graphical terrain entries with `type = urban` and usually `spawn_city = yes`
  make urban surfaces eligible for city models;
- `cities.bmp` selects a city-group index and `cities.txt` maps that index to
  meshes and density.

Adding a victory point does not automatically make its province visually
urban. Conversely, painting urban terrain does not create a victory point or
split a province. The editor should expose those as separate operations.

## Colormaps and DDS files

The common map DDS assets include:

- `colormap_rgb_cityemissivemask_a.dds`: RGB world tint plus alpha city lights;
- `colormap_water_0.dds`, `_1.dds`, `_2.dds`: water tint at successively lower
  resolutions;
- `fow_rgb_waterspec_a.dds`: fog-of-war/water-specular data;
- `atlas*.dds` and `atlas_normal*.dds`: terrain materials and normals.

The wiki describes the colormaps as 8.8.8.8 ARGB with no mipmaps and water
levels whose dimensions are halved at each level. Verify the actual header,
channel order, compression, dimensions, and mip chain against the installed
game before generating them. A visually plausible DDS can still be rejected
or render the vanilla world's coastline if its contract is wrong.

The exporter should classify each art file as one of:

1. generated and validated for the selected profile;
2. preserved byte-for-byte from an imported mod or dependency; or
3. intentionally omitted with a warning that the target inherits it.

"Present" alone is not a sufficient asset status.
